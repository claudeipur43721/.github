<p>把日历摊开往前倒推两周，你会发现问题不在于"选哪家"，而在于顺序：先开线路再想账号，往往绑错了还不知道；先绑账号再练切换，真出事时手忙脚乱。下面按 T-14 到 T+30 排一条时间线，每个节点写清要做的动作、要留下的产出物和验收标准。照着走一遍，主备切换这件事就从"看过文档"变成"闭着眼也能做"。</p>

<h2>一、T-14 到 T-7：先在纸上画清账号与线路的对应</h2>
<p>这一周不花钱，只做一件事：把现有账号、使用人、常用地区、是否绑了订阅，列成一张表。表里不许出现"大概"和"应该"，每个账号必须能指出它过去三十天主要从哪个地区登录。</p>
<h3>画一张对应关系图</h3>
<p>左边写账号编号，右边写计划使用的出口，中间画线。一条线只能连一个账号，一个账号也只能有一条主线。遇到"两个号共用一条线"的情况，先标红，等第二周再决定是拆还是保留。</p>
<h3>把备用线路也画上去</h3>
<p>主备关系要在纸上先成立。备用线可以是同城另一家，也可以是同家的第二段地址，但不能是"到时候再说"。实践里最常见的翻车不是主线路坏了，而是坏了之后发现备用线路从没验证过。</p>

<h2>二、T-6 到 T-3：开通、灰度、单点验证</h2>
<p>线路到手先不要碰正式账号。用一台干净的测试机，一套独立的浏览器配置，把连通性、属性、时延各验一遍。这一步的目的是把"能用"和"好用"分开判断。</p>
<h3>三项必测</h3>
<p>连通性用 <code>curl -x http://用户:密码@地址:端口 https://ipinfo.io/json</code>，确认出口 IP 与预期一致；属性用 whois 查 ASN 是否落在运营商段；时延按 183 篇的四段计时法跑二十次。三项都过，才进入下一步。</p>
<h3>灰度只用一个号</h3>
<p>选一个最不重要的账号先切，观察三到五天。这期间记录验证次数、重登次数、页面异常次数。三个数都平稳，再动第二个号。一次全量切换，出问题时你无法判断是线路的问题还是批次的问题。</p>

<h2>三、T-2 到 T-1：主备切换演练，练到不用查文档</h2>
<img src="/tp.png" alt="账号与住宅 IP 线路主备切换演练的时间节点安排">
<p>演练不是"知道怎么切"，而是"计时切一次"。把切换动作拆成可执行的步骤，写在一张卡片上，让实际值班的人照着做，记录每一步耗时。总时长超过十分钟的，就要优化。</p>
<h3>演练要记录的四个数</h3>
<p>发现故障耗时、决策耗时、执行切换耗时、切换后验证耗时。前两个是流程问题，后两个是技术问题。多数团队的瓶颈在前两个，因为没人敢拍板切。</p>
<h3>授权要提前给</h3>
<p>值班的人能不能在没请示的情况下切？不能的话，演练就是走过场。提前写清"何种现象下可直接切"，把决策权下放，比事后追责有用。</p>

<h2>四、上线首周：只观察，不调整</h2>
<p>这一周最难忍住的就是"再优化一下"。刚切完就改参数，等于把变量全搅在一起，后面出问题无法归因。规矩很简单：除非影响使用，否则一周内不动任何配置。</p>
<h3>每天记三行</h3>
<p>早上第一次登录是否顺畅、白天是否触发验证、晚上是否掉线。三行字，成本极低，一周后就能看出模式。很多人跳过这一步，结果一个月后只能凭印象说"好像还行"。</p>
<h3>把异常时间点标出来</h3>
<p>如果异常集中在某个固定时段，基本可以判定与线路拥塞相关；如果时间和地点都随机，则更可能是账号侧或环境侧的问题。这个区分决定了第二周该查哪里。</p>

<h2>五、第 8 天到第 30 天：把临时配置固化成文档</h2>
<p>临时配置的特点是"只有做的人知道"。三周内必须把它变成别人能看懂的东西，否则人员一变动，整套环境就成了黑盒。</p>
<h3>文档要写四块</h3>
<p>出口清单（地址、端口、归属、到期日）、账号对应关系、切换步骤、常见故障处置。四块都不长，加起来两三页，但必须包含具体的命令和判断条件，不能只写"检查网络"。</p>
<h3>密码管理别偷懒</h3>
<p>多个账号多条线，密码写在聊天记录里迟早出事。用密码管理器分组存放，把访问权限按人分配，谁看过谁没看过要能查得到。</p>

<h2>六、第 31 天之后：月度复盘只看三个数</h2>
<p>复盘不需要长篇大论，三个数就够：当月可用率、平均切换次数、平均恢复时长。三个数里有两个变差，就该考虑调整资源，而不是继续观察。</p>
<h3>续费决策挂在复盘上</h3>
<p>把每条线的到期日提前三十天写进日历，复盘时顺手判断续不续。等到期前三天才想起来，议价空间基本为零，还容易被迫接受涨价。</p>
<h3>季度做一次全量重测</h3>
<p>线路质量会随时间漂移，三个月前的测试结果不能当现在用。全量重测包括属性抽查、时延分布、切换演练各一次，成本半天，能避免很多"怎么突然变慢了"的困惑。</p>

<h2>常见问答</h2>
<h3>只有一条线，还需要做切换演练吗？</h3>
<p>答：需要，但演练的是"降级方案"：切到备用网络、暂停自动任务、通知使用人。没有备用线路时，能不能快速止损比能不能无缝切换更重要。</p>
<h3>两周的准备期是不是太长？</h3>
<p>答：如果账号数量在三个以内、没有订阅绑定，压缩到三到五天也合理。账号越多、绑定关系越复杂，准备期越不能省，因为返工成本远高于等待成本。</p>
<h3>切换后需要重新登录吗？</h3>
<p>答：多数情况下浏览器会保留会话，但出口地址变了之后，平台可能要求重新验证。演练时要把这一步算进耗时，别假设切换完就能直接用。</p>
<h3>主备两条线要买同一家吗？</h3>
<p>答：不建议。同一家的两条线往往共享上游，上游出问题时一起挂。主备分属不同上游，冗余才有意义，代价是要维护两套账号和账单。</p>
